### 1.2 数据结构

**特征文件** (每行一个候选):
```json
{
  "label": 0或1,           // 1=正解, 0=错误候选
  "group_id": "dev:1:1",   // 组ID, 同一查询的所有候选同组
  "query": "离心式泵",       // 查询文本
  "expected_ids": "A1-8-3", // 正确定额编号
  "quota_id": "A1-8-5",    // 当前候选的定额编号
  "quota_name": "...",     // 候选定额名
  "candidate_rank": 3,     // 候选在搜索结果中的排名
  "bm25_score": 12.5,      // BM25分数
  "confidence": 0.75,      // 系统给出的置信度
  "family_match": 1,       // 族匹配
  "dn_exact": 1,           // DN参数精确匹配
  "book_match": 1,         // 册匹配
  ...共75个特征
}
```

**组文件** (每组一个查询):
```json
{
  "group_id": "dev:1:1",
  "rows": 80,              // 该组候选数
  "positive_count": 2,     // 正解数
  "query": "离心式泵",
  "expected_ids": "A1-8-3|A1-8-5"
}
```

## 2. 特征分析

### 2.1 最具区分力的特征

| 特征 | Δ(正-负) | 含义 |
|---|---|---|
| candidate_rank | -27.5 | 正解通常搜索排名更靠前 |
| confidence | +17.5 | 正解置信度更高 |
| current_score | +0.32 | 正解当前评分更高 |
| bm25_score | +0.32 | 正解BM25分更高 |
| param_exact_count | +0.15 | 正解参数精确匹配更多 |
| book_conflict | -0.14 | 正解极少有册冲突 |
| dn_exact | +0.12 | 正解DN精确匹配更多 |
| token_overlap | +0.07 | 正解词元重叠更高 |

### 2.2 关键发现

- **排名信号最强**: candidate_rank 和 base_rank 的区分力远超其他特征。这说明搜索阶段已经做了大部分工作，排序阶段只需微调。
- **参数精确匹配重要**: param_exact_count, dn_exact, book_match 等精确匹配特征是强正信号。
- **冲突是强负信号**: book_conflict, has_param_conflict_reason 显著拉低概率。
- **当前排序弱项**: 31% top1 说明 69% 的正解被排到了后面。这些正解的特征分布与 top1 有细微差异，LTR可以学到。

## 3. 训练方案

### 3.1 模型选择

**LightGBM LambdaRank** — 专为排序优化的梯度提升树。

选择理由：
- 项目已有 LightGBM 加载代码 (`ltr_model_cache.py: _load_model` 使用 `lgb.Booster`)
- LambdaRank 直接优化 NDCG，比 pointwise 分类更适合排序
- 推理速度 < 1ms（25个候选 × 50棵树），对速度预算无影响
- 天然处理组内排序，正负样本不平衡不是问题

### 3.2 训练流程

```python
# 步骤1: 加载数据
#   - 读取 Dev + Hard 集 (有正解的组)
#   - 提取75个数值特征
#   - 构建 group 数组 (每组大小)
#   - 构建 label 数组 (1=正解, 0=其他)

# 步骤2: 特征工程
#   - 去掉常量特征 (方差=0)
#   - 去掉高相关特征 (|r| > 0.95)
#   - 保留 ~55个有效特征

# 步骤3: 训练
params = {
    'objective': 'lambdarank',
    'metric': 'ndcg',
    'ndcg_eval_at': [1, 3],
    'num_leaves': 31,
    'learning_rate': 0.05,
    'feature_fraction': 0.8,
    'bagging_fraction': 0.8,
    'bagging_freq': 5,
    'min_data_in_leaf': 20,
    'num_iterations': 200,
    'early_stopping_rounds': 20,
    'verbosity': -1,
}

# 步骤4: 评估
#   - Heldout集 NDCG@1, NDCG@3
#   - Goldenset端到端测评

# 步骤5: 输出
#   - ltr_v3_model.lgb (模型文件, ~500KB)
#   - ltr_v3_features.json (特征列表)
```

### 3.3 预期效果

基于特征分析和当前基线：

| 指标 | 当前 (手工排序) | LTR 预期 | 提升 |
|---|---|---|---|
| Dev Top1 | 31.2% | 40-45% | +10-15% |
| Dev Top3 | 50.7% | 55-60% | +5-10% |
| Goldenset Top1 | 60% (含经验库) | 63-68% | +3-8% |

LTR 主要改善的是"正解在候选池但被排到第2-3位"的场景（Dev集中占20%）。

### 3.4 为什么提升有限但值得做

LTR 不能解决召回失败（24%的组正解根本不在候选池）。但能解决排序失败：
- Dev 集 69% 的正解不在 top1 → LTR 可推回 ~15%
- 当前手工权重 = 纯猜测 → LTR 权重 = 从23万条数据中学到的

## 4. 部署方案

### 4.1 集成方式

当前 `ltr_ranker.py` 已有完整的 LTR 流水线：

```python
# 已有代码 (ltr_ranker.py:5779)
model = LTRModelCache.get_model(model_path)       # 加载模型
feature_names = [...]                              # 特征列表
predictions = model.predict(matrix)                # 推理
```

部署只需：
1. 将 `ltr_v3_model.lgb` 放到正确路径
2. 更新 `config.py` 中 `LTR_V2_MODEL_PATH` 指向新模型
3. 更新 `LTR_V2_FEATURES_PATH` 指向新特征列表

**无需修改任何业务代码**。

### 4.2 速度影响

- 模型加载: ~50ms（首次，全局缓存）
- 推理: ~0.3ms（25候选 × 50树 × LightGBM C++ 后端）
- 总增加: < 1ms/条

### 4.3 回退机制

已有代码中包含自动回退：
```python
# ltr_ranker.py:54-59
if not model_path.exists():
    cls._load_error = f"model_missing:{model_path}"
    return None, []  # 自动回退到手工评分
```
