
## 2. 反复出现的核心结论

### 2.1 R1 召回是最大瓶颈 (已确认4次)

| 文档 | 原话 |
|---|---|
| 4/8 检索路线图 | "优先补召回，再拉开排序差距" |
| 4/24 算法修复 | "召回命中率仍是 72.5%，R1_召回未命中还没有被修" |
| 4/24 R1诊断 | "R1 召回未命中 164，召回命中率 69.7%" |
| 我们实测 | "24/40 失败是召回问题，0/40 是排序问题" |

**结论：召回修了几个月没修好。每次 case-by-case 改一点，永远改不完。**

### 2.2 case-by-case 修复不可持续 (已确认)

R2-2a ~ R2-2e 的逐case修复记录：
- R2-2a: `changed_total=4, improved=4` (4/541 = 0.7%)
- R2-2b: 诊断通过, 不做代码修复
- R2-2c: 诊断通过, 不做代码修复
- R2-2d: `159/541→160/541` (1/541 = 0.2%)
- R2-2e: `changed_total=1, improved=1` (1/541 = 0.2%)

**5轮修复, 总提升 < 2%。用户说的"没完没了"就是这个。**

### 2.3 速度不是瓶颈 (已确认)

4/8 速度-质量主链：
> "现在不是所有样本都走长链。已经有 fast/standard/deep 分流。已经有 cache/prewarm/lightweight。真正的问题是快路径没命中后结束太早，或者标准路径投入不小但质量收益不够高。"

**速度优化已经做完了。当前 100条/104秒，2分钟预算够用。**

### 2.4 算法复杂度已被限制

V36 GOAL 协议：
> "默认不改算法；算法 patch 只有在 gate 明确授权且不需要人工确认时才允许。complexity_impact 只能是 decrease|neutral，increase 必须人工确认。"

## 3. 历史方案中哪些没做成

| 方案 | 目标 | 为什么没成 |
|---|---|---|
| LTR mixed safety | 保护组不退化 | do_not_break 持续失败 |
| R1 召回修复 | 召回 > 72.5% | 没进入执行 (一直卡在 R2) |
| V36 GOAL 自动化 | 全自动诊断→修复→验证 | 太复杂, pending 未推进 |
| Picker/CGR 修复 | 降低 R3/R4 | 没进入执行 |
| OpenClaw 二审 | LLM复核降低人工量 | 不让替代首轮匹配 |

## 4. 什么方法已经证明有效

| 方法 | 效果 | 边界 |
|---|---|---|
| LTR v2 模型 | +8.5% top1 | 只改善排序, 不改善召回 |
| 经验库 | +36% top1 (我们实测) | 依赖人工匹配数据积累 |
| 向量搜索 (chroma) | +3% top1 (我们实测) | 通用模型语义理解不足 |

## 5. 路线建议

历史文档和实测数据一致指向：

1. **核心矛盾是召回, 不是排序** (4份文档 + 我们实测都确认)
2. **case-by-case 修不完** (R2-2a~2e 5轮 < 2%)
3. **通用方案只有两条路**:
   - A. 微调向量模型 (改善召回, 通用, 可持续)
   - B. LLM 辅助 (改善难例, 但速度慢)

**推荐 A, 因为:**
- 4万条 OSS 人工配对现成
- SentenceTransformers 基础设施现成
- 训一次对所有清单生效 (不是修一个case)
- 加新省份数据→重训→自动变好
