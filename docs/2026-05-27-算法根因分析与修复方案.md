## 1. 系统概述

### 1.1 系统做什么

本系统（Jarvis）是一个建筑造价行业的**清单自动套定额**工具。用大白话说：

- **输入**：一条清单（例如"镀锌钢管 DN100 螺纹连接"），描述了某个建筑项目中要做什么工程
- **输出**：一条或多条匹配的定额（例如"C8-1-1 镀锌钢管(螺纹连接) 公称直径100mm以内"），即国家或省级计价标准中规定的工程单价
- **核心挑战**：每个省份的定额库有几万条定额，不同省份的定额编号和名称写法不同，但定额体系大体相通

### 1.2 核心数据资产

| 资产 | 说明 |
|---|---|
| OSS XML 母库 | 造价人员人工套完的定额结果（~14GB，数千个 XML），只覆盖部分省份，但定额体系大体相通，是高价值训练和参考数据 |
| `national_index.sqlite` | 百万级定额/清单数据 |
| `bill_library.db` | 清单项数据 |
| `experience.db` | 已完成项目的匹配记录（经验库），含权威层和候选层 |
| `universal_kb.db` | 跨省份通用知识库 |
| `ranking_feedback.db` | 用户纠正记录，含每次误排的维度分和主因 |

### 1.3 当前准确率基线

| 指标 | 值 | 来源 |
|---|---|---|
| 召回命中率（recall@20） | ~72.5% | `docs/global_repair_small_step_plan_v36.md` |
| Top1 命中率（hit_rate） | ~33.8% | 同上，LTR v2 full |
| Goldenset top1 | 0.75 | `tests/test_benchmark_regression.py` |
| Goldenset top3 | 0.83 | 同上 |
| Fastpath 精确率 | 0.90 | 同上 |

核心矛盾：**召回能找回 72.5% 的正确定额，但最终 top1 只有 33.8%。中间丢失的近 39 个百分点，就是排序算法的问题所在。**

## 2. 流水线全景

### 2.1 主流水线（按调用顺序）

```
输入清单
  │
  ├─ Step 1: 分类（classifiers.py）
  │   确定专业（电气/给排水/消防/土建/...）、册（book）、查询词
  │
  ├─ Step 2: 检索（hybrid_searcher.py）
  │   BM25 关键词搜索 + BGE 向量语义搜索 → RRF 融合 → Top 25 候选
  │
  ├─ Step 3: 经验库注入（experience_manager.py）
  │   查历史上相同/相似清单的匹配记录，作为高信任候选直接插入
  │
  ├─ Step 4: 重排序（reranker.py + ltr_ranker.py）
  │   CrossEncoder 模型对候选重新打分 → LTR 模型排序
  │
  ├─ Step 5: 参数验证（param_validator.py）
  │   检查候选定额的参数（管径/截面/功率/...）是否匹配清单要求
  │
  ├─ Step 6: 排序 + 拣选（candidate_scoring.py + constrained_ranker.py + orchestrator.py）
  │   两阶段排序（先按族选代表，再族内排） → CGR 门控 → 赛后修正
  │
  ├─ Step 7: 审核（gates.py + reconcilers.py）
  │   品类审查 / 材料审查 / 单价验证 / 规则注入
  │
  └─ 输出: 最终匹配结果 + 置信度
```

### 2.2 评分体系架构

系统内部同时存在 **四套评分体系**，彼此之间有重叠：

```
                    ┌──────────────────────┐
                    │   search_score       │  ← 检索时用（rerank 76% + name 16% + param 6%）
                    │   (candidate_scoring  │
                    │    :compute_          │
                    │    candidate_search_  │
                    │    score)             │
                    └──────┬───────────────┘
                           │
                    ┌──────▼───────────────┐
                    │   structured_score   │  ← 手工评分（param 10~28% + logic 18% + feature 14% + ...）
                    │   (candidate_scoring  │
                    │    :compute_          │
                    │    candidate_         │
                    │    structured_score)  │
                    └──────┬───────────────┘
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
  ┌──────▼──────┐  ┌──────▼──────┐  ┌──────▼──────────┐
  │ LTR score   │  │ CGR score   │  │ family/w_family │
  │ (XGBoost/   │  │ (语义+结构  │  │ score           │
  │  LightGBM   │  │  混合+     │  │ (两阶段排序用)  │
  │  模型预测)  │  │  softmax)  │  │                 │
  └─────────────┘  └─────────────┘  └─────────────────┘
```

当 LTR 模型不可用时，`structured_score` 作为后备。当 CGR 启用时，它在 LTR/手工结果之上再做一次排序。四套体系并行运行，**最终通过 `orchestrator.py` 中约 1100 行的赛后修正逻辑强行对齐**。

## 3. 十大问题详析

### 问题 1：全系统存在数十个硬编码权重，无标定依据

#### 现象

以下每个函数都包含手工估算的权重值，没有一个是从真实数据中学习得到的：

**`_compute_semantic_raw`（constrained_ranker.py:357-379）**—19 个加权项：

```python
return (
    hybrid_term * 0.22
    + _clip01(candidate.get("rerank_score", ...)) * 0.18
    + semantic_term * 0.16
    + spec_term * 0.10
    + _clip01(candidate.get("name_bonus")) * 0.08
    + _clip01(row.get("query_token_in_candidate_ratio", 0.0)) * 0.08
    + _clip01(row.get("candidate_token_in_query_ratio", 0.0)) * 0.06
    + _clip01(row.get("canonical_term_coverage", 0.0)) * 0.06
    + _clip01(row.get("core_term_bigram_jaccard", 0.0)) * 0.04
    + _clip01(row.get("raw_name_token_coverage", 0.0)) * 0.03
    + min(rank_term, 1.0) * 0.10
)
```

**`_compute_structural_raw`（constrained_ranker.py:441-468）**—24 个加权项：

```python
return (
    _clip01(candidate.get("param_score")) * 0.26
    + _clip01(candidate.get("logic_score", 0.5)) * 0.17
    + _clip01(candidate.get("feature_alignment_score", 0.5)) * 0.14
    + _clip01(candidate.get("context_alignment_score", 0.5)) * 0.08
    + rel_score * 0.09
    + exact_match * 0.08
    + material_match * 0.03
    + family_match * 0.04
    + entity_match * 0.03
    + system_match * 0.02
    + install_method_match * 0.02
    + connection_match * 0.01
    + ...（罚项）
    - family_conflict * 0.08
    - entity_conflict * 0.06
    - material_conflict * 0.04
    - system_conflict * 0.04
    - install_method_conflict * 0.03
    - connection_conflict * 0.02
    - reverse_tier * 0.06
    - negative_family_gate * 0.06
    - 0.10 * float(not candidate.get("param_match", True))
)
```

**`_family_selection_score`（candidate_scoring.py:249-281）**—14 个加权项，含非对称奖惩

**`_within_family_score`（candidate_scoring.py:296-317）**—11 个加权项

**`compute_candidate_structured_score`（candidate_scoring.py:510-534）**—根据 `strong_family` 条件动态切换权重

#### 影响

- 没有任何办法说清楚"权重为什么是这个值"
- 当特征分布发生变化（如新增省份、定额库更新），权重可能完全失效
- 无法做敏感性分析：不知道调哪个权重能提升准确率

#### 为什么之前没修

排权重需要大量的"正确答案→系统输出"配对来做网格搜索或贝叶斯优化。之前系统没有系统性地收集这些数据。好消息是：**`ranking_feedback.db` 现在已经在记录每次纠正时的维度分和误排主因——这正是权重标定需要的数据。**

### 问题 2：LTR 模型、CGR 门控、手工结构评分三重并行，赛后修正代码膨胀

#### 现象

当前流水线同时维护三个竞争性排序路径：

1. **LTR 模型路径**（`ltr_ranker.py`）：加载 XGBoost/LightGBM 模型对候选打分排序
2. **CGR 排序**（`constrained_ranker.py`）：语义分 + 结构分 → softmax → 概率排序
3. **手工结构评分**（`candidate_scoring.py`）：纯手工加权

这三条路径在 `rerank_candidates_with_ltr` 中并行运行：

```python
# ltr_ranker.py 中的简化逻辑
def rerank_candidates_with_ltr(item, candidates, context):
    # 第一步：手工评分 + 排序
    _annotate_manual_stage(candidates)            # 手工分数
    manual_ordered = _sort_with_stage_priority(candidates, ...)

    # 第二步：LTR 覆盖（如果模型可用）
    if ltr_model_available:
        ltr_scores = model.predict(feature_matrix)
        ltr_ordered = _sort_with_stage_priority(candidates, ...)
        # LTR 守护：手动结果好就不让 LTR 改
        ltr_ordered = _apply_ltr_guard(ltr_ordered, manual_ordered, ...)
    else:
        ltr_ordered = manual_ordered

    # 第三步：CGR 再覆盖
    if cgr_enabled:
        ranked, cgr_meta = apply_constrained_gated_ranker(item, candidates, context)
        # CGR 也会改变候选顺序

    return ranked, meta
```

当三者结果不一致时，`orchestrator.py` 中有约 1100 行的赛后修正逻辑来调和冲突：

```
_run_rank_pipeline()
  ├─ _promote_family_group_stronger_candidate()     # ~160 行
  ├─ _promote_rankable_contract_structural_candidate() # ~180 行
  ├─ _promote_post_ltr_structural_candidate()        # ~70 行
  ├─ _promote_lifecycle_stronger_candidate()          # ~55 行
  ├─ _record_decision_advisory() 系统                # ~50 行
  └─ _weak_family_group_advisory_rejection()         # ~100 行
```

#### 影响

- 赛后修正本质上是**对排序器不信任的补丁**。每一个补丁都在说"我知道排序器在这里会出错"
- 累加的补丁让整个系统变得难以调试：一个候选被赛后提升了 3 次又被降了 2 次，最终排名几乎不可能追溯
- 修改任何一个排序器的权重都可能导致赛后修正逻辑连锁崩溃

#### 根因

这是架构设计问题。LTR 模型最初是"增强"角色，CGR 后来加入作为"安全门控"，手工评分是"后备"——但三个角色从未被清晰定义边界。

### 问题 3：两阶段排序的族代表机制存在路径依赖

#### 现象

`two_stage_sort`（candidate_scoring.py:660-731）的工作方式：

```
第一步：按"族"分组
  族A（管道类）: [候选A1, 候选A2, 候选A3, ...]
  族B（阀门类）: [候选B1, 候选B2, ...]
  族C（支架类）: [候选C1, ...]

第二步：每个族选一个"代表"
  族A 代表 = 族A 中 _family_stage_rank_key 得分最高的候选
  族B 代表 = 族B 中得分最高的候选

第三步：按代表的得分对族排序
  族B（代表得分 0.92）> 族A（代表得分 0.88）> 族C（代表得分 0.45）

第四步：族内排序（按 _within_family_rank_key）
  输出: [B1, B2, A1, A3, A2, C1, ...]
```

**问题在这里**：如果族 A 的代表被错误标记了 `family_gate_hard_conflict`，整个族 A 都会被沉到底部，即使族 A 中有很好的候选。

`_family_stage_rank_key` 中的第一个排序键就是：

```python
(
    1 if not _has_fatal_rank_conflict(candidate) else 0,  # ← 这个！
    1 if _has_exact_experience_anchor(candidate) else 0,
    1 if family_supported else 0,
    family_stage_priority,
    ...
)
```

一个伪阳性冲突会让代表得分从第一位直接掉到最后一位，拖累整个族。

#### 为什么它危险

硬冲突中的三个标志——`family_gate_hard_conflict`、`feature_alignment_hard_conflict`、`logic_hard_conflict`——都是由基于规则的系统设置的，而基于规则的系统必然有误报。一次误报乘以族代表的放大效应，可能导致系统性错配。

### 问题 4：CGR 门控判定全部由硬编码 logit 驱动

#### 现象

CGR（Constrained Gated Ranker）是候选能否被接受的最后一道自动门控。它的核心判定分两步：

**Gate 分值**（`_compute_gate`，constrained_ranker.py:504-517）：

```python
logit = (
    0.18
    - 1.80 * query_param_coverage
    + 1.30 * group_ambiguity_score
    - 0.75 * family_confidence
    - 0.30 * has_material
    - 0.25 * has_install_method
    - 0.40 * has_hard_book_constraints
    + _route_adjustment(route)
    + 0.025 * min(candidate_count, 20)
)
gate = sigmoid(logit)
```

Gate 决定了语义分与结构分的混合比例。gate 越接近 1，越偏语义；越接近 0，越偏结构。

**Accept 判定**（`_attach_accept_head`，constrained_ranker.py:646-665）：

```python
accept_logit = (
    -1.00
    + 4.20 * (p1 - 0.40)
    + 5.80 * gap12
    + 2.80 * gap13
    + 0.90 * query_param_coverage
    + 0.45 * family_confidence
    - 1.40 * group_ambiguity_score
    - 1.60 * tier_penalty
    - 0.80 * generic_penalty
    - 1.60 * int(fatal_hard_conflict(top))
    + 0.15 * has_material
    + 0.15 * has_install_method
)
# route 调整
if route == "installation_spec":
    accept_logit += 0.20
elif route == "ambiguous_short":
    accept_logit -= 0.20

accept = (accept_score >= threshold and p1 >= min_prob
          and not fatal_hard_conflict and feasible)
```

#### 影响

这些系数不是从数据中学习得到的。系数的大小反映了开发者对各因素的"直觉权重"而非实际预测能力。例如 `4.20 * (p1 - 0.40)` 表示"top1 概率每高 0.01，通过的门槛就降低 0.042"——这个数字没有实证依据。

#### 为什么重要

CGR 的 accept 判定直接影响最终输出：accept=false 的结果会被标记为需人工审核，实质上等同于系统"放弃"这条清单。如果门控太严，好结果被拒；太松，坏结果通过。

### 问题 5：多处存在系统性非对称偏差

#### 5a. 族门控惩罚力度是奖励的两倍

`_family_selection_score`（candidate_scoring.py:264-267）：

```python
if family_gate > 0:
    score += family_gate * 0.03     # 正向：奖励 0.03 每单位
elif family_gate < 0:
    score += family_gate * 0.06     # 负向：惩罚 0.06 每单位（= -0.06 每单位）
```

这意味着系统对"不太确定是不是同一族"比"确定是同一族"更敏感——系统倾向于**过度回避不确定性**。

#### 5b. 路由调整偏差巨大

`_route_adjustment`（constrained_ranker.py:224-233）：

```python
def _route_adjustment(route: str) -> float:
    if route == "installation_spec":
        return -0.65    # 安装规格型：大幅压制
    if route == "material":
        return -0.25    # 材料型：中等压制
    if route == "semantic_description":
        return +0.35    # 语义描述型：提升
    if route == "ambiguous_short":
        return +0.50    # 短歧义型：大幅提升
    return 0.0
```

`installation_spec` 和 `ambiguous_short` 之间的差距是 **1.15**，在 sigmoid 空间中这足以让 gate 值从 0.1 变成 0.9——也就是完全翻转语义与结构的混合比例。

#### 5c. 范围冲突对经验锚点"豁免"

`_family_selection_score` 和 `_within_family_score` 中都有这样的逻辑：

```python
if _candidate_scope_conflict(candidate) and not _has_exact_experience_anchor(candidate):
    score -= 0.08
```

这意味着如果候选来自经验库（历史上匹配过），即使它和当前清单的范围冲突，也不会被惩罚。但经验库也可能有错——特别是权威层的错误会被无限复制。

### 问题 6：置信度标定是伪造的——手工 isotonic 映射且上限封顶

#### 现象

`DEFAULT_CONFIDENCE_SPEC`（confidence_calibrator.py:39-64）定义了一个手工调参的 isotonic 校准表：

```python
isotonic_points=(
    (0.00, 0.05),   # 模型输出 0.00 分 → 实际置信度 5%
    (0.20, 0.16),   # 模型输出 0.20 分 → 实际置信度 16%
    (0.40, 0.35),
    (0.55, 0.55),
    (0.70, 0.72),
    (0.82, 0.84),
    (0.90, 0.90),
    (0.96, 0.95),   # ← 最高只到 95%
    (1.00, 0.95),   # ← 1.00 分也被压缩到 95%
)
```

同时有一个 `ambiguous_short_ceiling=75`：短歧义型清单的置信度最高只到 75%。

#### 影响

- 分值 0.96 以上的匹配被强行压制在 95%，系统永远不能说出"99% 确定"——即使匹配是完全精确的
- 短清单（如"混凝土 C30"）即使套得非常准确，也只显示 75% 的置信度，对用户来说是误导
- 这个表不是从 goldenset 的真实 top1 率计算出来的——它是手工调的

#### 正确的做法

Isotonic 校准应该从 **goldenset 中每个置信度区间内的实际准确率** 计算：

1. 把 goldenset 的 100 个样本按模型输出的置信度排序
2. 分成 10 个桶
3. 每个桶的"实际准确率"就是该桶内预测正确的比例
4. 用实际准确率作为 isotonic 映射的 calibrated 值

```python
_VENTILATION_VALVE_KEYWORDS = ("止回阀", "防火阀", "排烟防火阀", "调节阀", ...)
```

#### 影响

- 遗漏一个关键词 = 系统对某类清单静默地做出错误处理
- 不同省份的定额表述不同，"增加费"在北京可能是费用项，在宁夏就可能是实体项
- 新增关键词需要改代码、跑测试、部署——对于造价人员来说这是不可操作的

### 问题 8：OSS 召回先验使用未标定的词项重叠权重

#### 现象

OSS 召回先验（`oss_recall_prior.py:234-243`）用简单的加权词项重叠来评分候选定额：

```python
score = (
    overlap * 1.0
    + (2.5 if exact_name else 0.0)    # 清单名完全匹配 → 大幅加分
    + quota_name_overlap * 0.6         # 定额名词项重叠
    + quota_specific_overlap * 1.2     # 非通用词项重叠（核心信号）
    + specific_overlap * 0.9
    + bill_overlap * 0.25              # 清单词项重叠（权重很低）
    + min(candidate.support_count, 8) * 0.15
    + candidate.source_family_count * 0.35
)
```

同时，通用词过滤只包含 10 个英文词：

```python
GENERIC_TERMS = {
    "concrete", "pipe", "pump", "rebar", "support",
    "install", "make", "made", "work", "project",
}
```

而系统中处理的是中文建筑术语（"混凝土"、"管道"、"安装"、"制作"、"工程"等），英文通用词过滤几乎无效。

#### 影响

- OSS 来自人工套定额的结果，是高价值信号。权重不标定 = 浪费信号
- 中文通用词（"安装"、"制作"、"施工"等）没有被过滤，导致"安装"这种高频词被当成特异性信号来使用

### 问题 9：多源先验分数累加无上界

#### 现象

`compute_candidate_prior_score`（candidate_scoring.py:362-394）：

```python
def compute_candidate_prior_score(candidate: dict) -> float:
    ...
    if "experience" in knowledge_sources:
        if authority_experience:
            return 0.10 * prior_score    # 最高 0.12（prior_score 最高 1.2）
        return 0.06 * prior_score

    if "universal_kb" in knowledge_sources:
        if exact_kb:
            return 0.05 * prior_score    # 最高 0.06
        return 0.03 * prior_score

    if "quota_alias" in knowledge_sources:
        if exact_alias:
            return 0.08 * prior_score    # 最高 0.096
        return 0.04 * prior_score
```

虽然函数本身只返回单一来源的分数（用 `if/elif` 隐式实现），但调用方在多处将这些先验分数**累加**到总排名分中。例如 `_family_selection_score` 中的 `+ prior_score`（第 260 行），`compute_candidate_structured_score` 中的 `+ prior_score`（第 519 行）。

#### 影响

先验分数从信息源角度看是**记忆**（"历史上这条清单匹配过这个定额"），而从排序角度看它和语义相关性（"这条定额的语义和清单最接近"）被等同对待。当先验分数（0.12）加上族匹配加分（+0.10）加上逻辑精确匹配（+0.03）后，一个"曾经正确但现在可能不再适用"的候选完全可能压制一个"语义完美匹配但从没见过"的候选。

### 问题 10：赛后修正代码量说明模型排序不充分

#### 现象

`_run_rank_pipeline`（orchestrator.py:2972-4103）约 1100 行，其中大部分是赛后修正：

```
_run_rank_pipeline 主结构（简化）：
  1. record_decision_advisory 内部函数定义     (~50 行)
  2. 赛后促进逻辑:
     - promote_family_group_stronger           (~160 行)
     - promote_rankable_contract_structural    (~180 行)
     - promote_post_ltr_structural             (~70 行)
     - promote_lifecycle_stronger              (~55 行)
  3. 族 advisory 拒绝逻辑:
     - weak_family_group_advisory_rejection    (~100 行)
  4. 各种仲裁逻辑                              (~200 行)
  5. 跟踪/诊断                                 (~200 行)
```

赛后促进函数的核心逻辑是：

> "排序器选了候选 X 作为 top1，但我看到了 Y 在以下方面更好：参数匹配、结构证据、族对齐……让我把 Y 推到 top1。"

这本质上是**重新实现了一个排序器**，但它比真正的排序器更差——因为它只能看到 top1 和附近的候选，看不到全局顺序。

#### 为什么这是问题

- 每增加一个促进逻辑，系统的行为就变得更难预测
- 促进逻辑之间可能相互冲突（A 促进 Y 超过 X，B 促进 Z 超过 Y）
- 追踪一个候选的最终排名需要理解 5+ 层的促进/拒绝逻辑和平共 20+ 条规则

### 阶段 2：从反馈数据标定权重（P0-1a）

**目标**：用真实的"用户纠正"数据来重新标定评分权重。

**前置条件**：检查 `ranking_feedback.db` 中是否有足够多的纠正记录（≥ 50 条不同类型）

**新增文件**：`src/weight_calibrator.py`

**核心原理**：

`ranking_feedback.db` 中的每条纠正记录包含：
- `query_text`：清单文本
- `selected_quota_id`：用户最终选中的定额（正确答案）
- `original_top1_quota_id`：系统原来推荐的定额（错误答案或次优答案）
- `dimension_scores_json`：各个维度的分数（文本相似度、专业匹配度、单位匹配度、材料匹配度、来源可信度、共识因子）
- `misrank_primary_factor`：系统判定这次误排的主要原因

权重标定器的工作流程：

```
1. 从 ranking_feedback.db 加载所有纠正记录
2. 将记录分为两组：
   - "正确组"：用户确认的匹配（signal='confirm'）
   - "纠正组"：用户改正的匹配（signal='correct'），包含正确答案
3. 对每组中的每条记录：
   a. 重新运行搜索 → 得到候选列表
   b. 对候选列表应用不同的权重组合
   c. 记录哪种权重组合能让"正确组"的正确答案排第一
4. 目标函数：
   maximize: 正确组 top1 率 × 0.7 + 纠正组正确答案进入 top3 率 × 0.3
5. 输出使得分最高的权重到 db/common/calibrated_weights.json
```

**改动文件**：

- `src/candidate_scoring.py`：新增 `_load_calibrated_weights()`，优先使用标定后的权重
- `config.py`：新增 `CALIBRATED_WEIGHTS_PATH` 和 `SCORING_WEIGHT_VERSION`

**验收标准**：

- `weight_calibrator.py` 能正常运行并输出 JSON
- goldenset 上 top1 ≥ 基线 +0.02 或保持不变
- ECE 不恶化

**风险**：中。如果 feedback 数据有偏差（比如只在某些专业有纠正记录），权重可能对这些专业过拟合。

### 阶段 3：用 goldenset 标定置信度（P0-1b）

**目标**：把手工调的 isotonic 映射替换为从真实准确率计算的映射。

**改动文件**：`src/confidence_calibrator.py`

**具体改动**：

`_load_calibrated_spec()` 的新逻辑：

```
1. 加载 eval/golden_set.jsonl（100 条人工确认的正确匹配）
2. 对每条 golden 记录，用当前系统跑匹配，得到原始置信度分数
3. 将 100 个 (原始分数, 是否正确) 配对按原始分数排序
4. 分成 10 个等大小的桶
5. 每个桶的 calibrated 值 = 桶内正确匹配的比例
   （例如原始分数 0.80-0.85 的桶里 8/10 是正确的 → calibrated = 0.80）
6. 输出 isotonic_points 到 db/common/confidence_calibration.json
```

同时移除 `ambiguous_short_ceiling=75` 的限制——改为从数据中自然学习短清单的准确率是否真的更低。

**验收标准**：

- ECE ≤ 0.08（校准后预测置信度与实际准确率的差异 ≤ 8%）
- 高置信度段（≥ 90%）的实际准确率 ≥ 90%

**风险**：中。goldenset 只有 100 条，对低置信度区间的校准可能不够稳定。

### 阶段 4：修复两阶段排序的代表选择（P1-2d）

**目标**：防止单个被误标记的族代表拖累整个族。

**改动文件**：`src/candidate_scoring.py`

**具体改动**：

`two_stage_sort` 中的代表选择逻辑改为：

```
当前逻辑：
  representative = max(group, key=_family_stage_rank_key)
  → 只取第一名，任何对第一名的误判都放大到整个族

新逻辑：
  candidates_sorted = sorted(group, key=_within_family_score, reverse=True)
  top3 = candidates_sorted[:3]
  representative = weighted_vote(top3, weights=[0.5, 0.3, 0.2])

  # 如果加权代表有 fatal_hard_conflict，跳过，用第二名
  if _has_fatal_rank_conflict(representative):
      representative = top3[1]
```

**验收标准**：

- `pytest tests/test_two_stage_family_conflict_recovery.py`（新增测试）通过
- goldenset top1 准确率不下降
- 硬冲突候选不再出现在 final top1 位置（检查测评日志）

**风险**：低。改动只在 bucket 排序逻辑中，不影响单候选评分。

### 阶段 5：统一排序框架（P1-2a + 2b）

**目标**：LTR 模型是唯一排序器，CGR 只做门控判断，手工评分只做后备。

**这步改动范围最大，需要分三步走。**

#### 5a. 解耦 CGR 门控与排序（~200 行）

改动 `src/constrained_ranker.py`：

```
当前 apply_constrained_gated_ranker 做三件事：
  1. 计算语义/结构特征 → 打分
  2. softmax → 排序
  3. accept head → 通过/不通过判定

拆分后：
  _compute_cgr_features(item, candidates, context) → dict
    只提取特征，不排序不评分

  apply_cgr_gate(ranked_candidates, features) → dict
    只做门控判断，返回 {accept: bool, accept_score: float, ...}
    不修改候选顺序
```

#### 5b. LTR 作为唯一排序源（~120 行）

改动 `src/ltr_ranker.py`：

```
当前 rerank_candidates_with_ltr：
  手工排序 → LTR 覆盖 → LTR guard → CGR 覆盖

改为：
  if LTR 模型可用:
      LTR 排序（唯一排序源）
  else:
      手工评分排序（后备，仅当模型加载失败时使用）
  CGR 门控（只判断通过/不通过，不重新排序）
```

删除 `_rank_score_source` 切换逻辑，统一 `rank_score = ltr_score or manual_score`。

#### 5c. 删除赛后修正（~400 行删除）

改动 `src/match_pipeline/orchestrator.py` 和 `src/ltr_ranker.py`：

删除以下函数（在阶段 5b 验证通过后）：
- `_promote_family_group_stronger_candidate`
- `_promote_rankable_contract_structural_candidate`
- `_promote_post_ltr_structural_candidate`
- `_promote_lifecycle_stronger_candidate`
- `_weak_family_group_advisory_rejection`
- `_record_decision_advisory` / `_record_post_ltr_structural_advisory`
- `_apply_ltr_guard`

**验收标准**：

- goldenset top1 ≥ 基线
- 删除代码后 `pytest tests/test_match_pipeline_*.py -x` 通过
- 手工抽查 10 条不同类型的清单，确认匹配质量无退化

**风险**：高。这是核心流水线改动，需要阶段 1-4 的积累作为安全网。
