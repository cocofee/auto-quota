```

                                                    这里用硬编码权重

```


### 1.4 速度基线

| 阶段 | 耗时 | 占比 |
|---|---|---|
| 分类 + 路由 | ~5ms | <1% |
| BM25 检索 | ~50ms | 5% |
| 向量检索 | ~200ms | 19% |
| 重排序(CrossEncoder) | ~500ms | 48% |
| 参数验证 | ~100ms | 10% |
| 手工评分排序 | ~80ms | 8% |

2 分钟预算 = 120 秒，当前 104 秒。

**LTR 模型推理：< 1ms（LightGBM on 25 candidates × 75 features）。完全不影响速度。**

## 2. 架构设计

### 2.1 目标架构

```
输入清单 → 分类 → 检索(BM25+向量+OSS召回+经验库) → 重排序 → 参数验证
                                                           ↓
                               ┌── LTR 模型排序（LightGBM）← 75维特征
                               ↓
                          CGR 门控判定
                               ↓
                            输出
```

### 2.2 当前 vs 目标

| | 当前 | 目标 |
|---|---|---|
| 排序方式 | 手工硬编码权重 | LightGBM LambdaRank |
| 权重来源 | 猜测 | 14万条数据训练 |
| CGR gate | 硬编码 logit | LTR 训练时联合标定 |
| OSS 数据 | 索引已构建但未启用 | 开启召回 + 经验库注入 |
| 赛后修正 | 默认关闭（可开关） | 删除 |

## 3. 实施步骤

### 步骤 1：训练 LightGBM 排序模型（离线，~30 分钟）

**输入：** `ltr_features_dev.jsonl` + `ltr_group_dev.jsonl`

**流程：**
```python
# 1. 加载数据：解析 JSONL，按 group_id 分组
# 2. 特征选择：75 个特征中去掉常量、高相关特征 → ~50 个有效特征
# 3. 划分：dev 集内 80/20 分割（或直接用 hard/heldout 做验证）
# 4. 训练：LightGBM LambdaRank
#    - objective: lambdarank
#    - metric: ndcg@1, ndcg@3
#    - num_leaves: 31
#    - learning_rate: 0.05
#    - n_estimators: 200（早停）
# 5. 评估：在 heldout 上计算 NDCG@1, NDCG@3, top1 accuracy
# 6. 输出：ltr_v3_model.lgb + ltr_v3_features.json
```

**关键：正负样本不平衡（1:93）**
- LambdaRank 天然处理不平衡（只看组内排序，不关心全局正负比）
- 只需确保每组至少有 1 个正样本——422 组无正样本的跳过
- 最终可用组：1,767 - 422 = 1,345 组

**预期效果：**
- 开发集 NDCG@1 > 0.65
- Heldout NDCG@1 > 0.55

**速度影响：** 0（离线训练）

---

### 步骤 2：部署模型到流水线（< 50 行改动）

**改动文件：** `config.py` + `src/ltr_ranker.py`

当前逻辑（ltr_ranker.py:5779）：
```python
predictions = model.predict(matrix)
```

部署仅需：
1. 将 `ltr_v3_model.lgb` 放到 `data/` 下
2. 更新 `config.py` 中 `LTR_V2_MODEL_PATH` 指向新模型
3. `ltr_ranker.py` 中已有完整的特征提取 → 预测 → 排序流程，无需改动

模型加载已有缓存机制（`LTRModelCache`），首次加载 ~50ms，后续 0ms。

**速度影响：** 每条清单 +0.5ms（LightGBM 预测 25 个候选）

---

### 步骤 3：开启 OSS 召回 + 经验库注入（配置改动）

当前这些模块已集成但未启用：

```python
# config.py 中已有的开关
OSS_RECALL_INDEX_ENABLED = True   # 开启 OSS 召回索引
OSS_GUARDED_ALIAS_ENABLED = True  # 开启别名索引
SEARCH_EXPERIENCE_INJECTION_ENABLED = True  # 开启经验库注入
```

OSS 召回索引（`oss_recall_index_17x_v2.jsonl`）在检索阶段额外注入 1-3 个高置信候选。流程：
1. 清单分词 → 查索引 → 找到跨省匹配的定额编号
2. 将编号对应到当前省份的定额（通过 national_index 映射）
3. 注入到候选池，标记 `knowledge_prior_sources=["oss_recall"]`

**速度影响：** +2ms/条（SQLite + JSONL 内存索引）

经验库注入：查 experience.db 中相同/相似清单的历史匹配。
**速度影响：** +3ms/条（FTS5 全文索引）

---

### 步骤 5：标定 CGR Gate 参数（离线）

当前 CGR gate 使用硬编码 logit。有了 LTR 概率分数后可重新标定：

1. 在 heldout 集上跑匹配，收集 (LTR score, CGR gate, is_correct) 三元组
2. 拟合 isotonic 回归：LTR score → accept 概率
3. 替代当前的硬编码 `_compute_gate` 和 `_attach_accept_head`

**速度影响：** 0（离线标定）

## 4. 速度预算

| 阶段 | 当前 | 加 LTR | 加 OSS召回 | 加经验库 | 最终 |
|---|---|---|---|---|---|
| 分类+路由 | 5ms | 5ms | 5ms | 5ms | 5ms |
| 检索 | 250ms | 250ms | 252ms | 255ms | **257ms** |
| 重排序 | 500ms | 500ms | 500ms | 500ms | 500ms |
| 参数验证 | 100ms | 100ms | 100ms | 100ms | 100ms |
| 排序 | 80ms | 80ms | 80ms | 80ms | **81ms** |
| CGR+后处理 | 100ms | 100ms | 100ms | 100ms | 100ms |
| **合计** | **1037ms** | **1037ms** | **1039ms** | **1042ms** | **1043ms** |

100 条：**104.3 秒**，2 分钟预算剩余 **15.7 秒**。✅

**风险点：** 重排序 CrossEncoder 占 48%。如果省不掉，考虑：
- 减少重排序候选数：25 → 15（省 ~200ms）
- 仅在 LTR 低置信时触发重排序

## 6. 风险与回滚

| 风险 | 概率 | 缓解 |
|---|---|---|
| LTR 模型过拟合（NDCG 高但实际差） | 中 | 用 heldout 集独立验证，不调参到过拟合 |
| LTR 比手工评分更差 | 低 | 模型加载失败自动回退到手工评分（已有机制） |
| 经验库注入后速度超标 | 低 | 限制经验库查询候选数 ≤ 3，FTS5 索引已建 |
| OSS 数据偏差（福建多、其他省少） | 中 | 训练时按省份加权采样 |
