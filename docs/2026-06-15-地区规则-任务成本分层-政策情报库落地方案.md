# JARVIS 三项务实建议落地方案（2026-06-15）

## 结论

三项建议按“先补元数据和台账，不改核心匹配算法”的方式落地，避免干扰当前 OSS/LTR 调优：

1. 给文件入口与任务上下文补齐地区规则字段。
2. 建立脚本 / 模型 / Agent 三层任务路由与升级条件。
3. 建立带证据链、需人工确认的造价政策情报库。

当前仓库有未提交的算法与前端改动，本轮不触碰这些文件，只新增本方案和可直接使用的政策种子台账。

---

## 一、地区规则识别

### 1. 最小字段集

在现有 `province` 基础上增加以下字段。第一阶段可先存入任务/文件入口 JSON 扩展字段，稳定后再迁移数据库：

```json
{
  "region": {
    "province": "江苏省",
    "city": "苏州市",
    "district": "",
    "confidence": 0.92,
    "evidence": ["文件封面：苏州市……", "编制说明：执行苏住建价〔……〕"]
  },
  "pricing_standard": {
    "name": "建设工程工程量清单计价标准",
    "edition": "2024",
    "standard_no": "GB/T 50500-2024",
    "effective_date": "2026-06-01",
    "applicability": "苏州市行政区域内相关工程",
    "confidence": 0.88,
    "source_refs": []
  },
  "rule_resolution": {
    "status": "resolved",
    "conflicts": [],
    "manual_review_required": false
  }
}
```

### 2. 识别优先级

按以下证据顺序识别，不用文件名单点定案：

1. 招标文件、编制说明、合同专用条款中的明确适用条款。
2. 工程所在地、建设单位所在地、项目地址。
3. 清单/计价文件中的定额库名称、计价依据、费用文件编号。
4. 文件元数据和文件名。
5. 无可靠证据时保留为空并转人工确认。

### 3. 冲突处理

- 工程所在地与声明适用规则冲突：以正式编制/招标文件为高优先级，但必须标记冲突。
- 同时出现国家标准与地方细则：两者并存，地方细则作为补充约束，不覆盖国家标准原文。
- 只有省份、没有城市：允许省级规则匹配，不推测城市。
- 规则执行日期晚于项目编制日期：不自动应用，转人工审核。

### 4. 接入点

优先接入已有能力：

- `/api/file-intake/upload`：接收 `province/city/project_date` 等提示。
- `classify/parse`：从正文抽取地区、文件号、标准号、执行日期。
- `/api/openclaw/qmd-search`：使用 `province/specialty/status` 过滤规则证据。
- `OpenClawReviewService.build_review_context`：追加地区规则摘要与冲突提示。

### 5. 验收标准

- 10 个不同地区样本中，能输出地区、标准版本、证据和置信度。
- 无证据时不猜测；有冲突时必出警告。
- 规则命中可追溯到官方原文或项目文件页码/段落。
- 不因增加地区字段改变现有定额候选排序结果。

## 二、Agent 任务成本分层

### 1. 三层路由

| 层级 | 执行方式 | 适用任务 | 禁止事项 |
|---|---|---|---|
| L0 低成本 | 本地脚本/规则 | 目录扫描、格式识别、哈希去重、字段清洗、标准号/日期正则抽取 | 不做语义定案 |
| L1 中成本 | 单次模型调用 | 表格理解、文档分类、地区/标准候选抽取、异常摘要 | 不直接写正式知识，不批量无限重试 |
| L2 高成本 | Agent 工作流 | 复杂项目复核、多文件交叉验证、失败回退、策略生成 | 未满足升级条件不得调用 |

### 2. 默认路由规则

```yaml
routing:
  default: L0
  promote_to_L1_when:
    - structured_extraction_failed
    - document_semantics_required
    - conflicting_regex_signals
  promote_to_L2_when:
    - multi_document_cross_check_required
    - L1_confidence_below_0_75
    - policy_conflict_affects_pricing
    - human_requested_deep_review
  never_auto_promote_when:
    - duplicate_file
    - unsupported_or_corrupt_file
    - missing_required_source_document
```

### 3. 每次任务必须记录

- `task_id`
- `task_type`
- `cost_tier`
- `promoted_from`
- `promotion_reason`
- `model/provider`（如有）
- `input_count/output_count`
- `duration_ms`
- `retry_count`
- `result_status`
- `human_value`：是否形成可用结果/是否减少人工复核

### 4. 控制原则

- 批量任务先 L0 去重、切分、筛选，再把少量不确定项送模型。
- L1 默认一次请求完成一批同构项目，禁止逐行调用模型。
- L2 只处理高风险、高不确定、需跨文件推理的任务。
- 同一失败原因最多自动重试 1 次；再次失败进入人工队列。
- 成本统计先按“调用次数、输入项、耗时”记账；价格字段作为可选项，避免绑定某家模型计费规则。

### 5. 验收标准

- 每个任务可解释为什么进入 L0/L1/L2。
- 目录扫描和基础字段抽取不消耗模型额度。
- 可按日统计三层任务数量、失败率、升级率和人工采用率。
- 高成本 Agent 输入量相较未分层基线显著下降，且不降低最终审核覆盖率。

## 三、造价标准 / 电子数据交换 / 招投标 AI 政策情报库

### 1. 存储原则

复用现有链路：

`官方原文 -> source_pack -> staging 候选 -> 人工审核 -> knowledge_wiki/QMD -> JARVIS 检索`

不另建一套不可追溯的“政策数据库”；台账只负责结构化索引，正式结论仍须保留 `source_refs`。

### 2. 最小记录结构

```json
{
  "policy_id": "policy-20260615-001",
  "title": "",
  "issuer": "",
  "document_no": "",
  "published_date": "",
  "effective_date": "",
  "expiry_date": "",
  "province": "",
  "city": "",
  "topic": "pricing_standard|data_exchange|tender_ai|other",
  "applicable_stage": ["招标", "投标", "计价", "结算"],
  "applicable_specialty": [],
  "status": "candidate|verified|effective|expired|superseded",
  "official_url": "",
  "source_refs": [],
  "impact_summary": "",
  "jarvis_actions": [],
  "reviewed_by": "",
  "reviewed_at": ""
}
```

### 3. 入库门槛

- 优先收录政府、住建部门、国家标准平台等官方来源。
- 搜索摘要、媒体转载只能作为线索，不能标记 `verified/effective`。
- 必须区分发布日期、执行日期、失效日期。
- 必须写明适用地区、工程阶段和对现有流程的影响。
- 新规则不能自动改写正式匹配逻辑；先进入 staging，经人工确认再晋升。

### 4. 首批专题

1. 2024 版清单计价标准及各地执行细则。
2. 各省市工程造价电子数据交换标准及修订动态。
3. 招投标 AI 应用、电子招投标、智能评审和围串标识别政策。
4. 与 JARVIS 当前瓶颈直接相关的主材价格、价差调整和合同调价规则。

### 4.1 招投标 AI 场景优先标签

JARVIS 造价规则库先补齐以下四类标签，和国家发改委“AI+招投标”场景保持一致。标签先用于知识候选、检索过滤和审核提示，不直接改写正式计价判断。

| 标签 | 适用对象 | JARVIS 应做的事 | 典型证据 |
|---|---|---|---|
| `tender_doc_check` 招标文件检测 | 招标文件、清单、控制价、合同条款 | 检测缺项、前后矛盾、计价依据不一致、资格/评分条款异常、清单特征与图纸不一致 | 招标文件章节、清单项、合同专用条款、答疑澄清 |
| `bid_compliance_selfcheck` 投标合规自查 | 投标报价、技术标、商务标、响应文件 | 检查格式、签章、资质、报价一致性、不可竞争费、暂列金/暂估价、响应偏离 | 投标文件、报价汇总、措施费表、规费税金表 |
| `collusion_risk_feature` 围串标特征 | 多投标人报价、清单单价、文件元数据、异常相似文本 | 标记高相似报价、规律性差异、异常一致错误、文件制作痕迹、IP/时间/元数据线索；仅做风险提示 | 多家投标文件、报价明细、电子交易平台记录、评标异常记录 |
| `credit_management` 信用管理 | 企业资质、人员证书、处罚记录、信用评价、黑名单/红名单 | 检查信用约束、失信/处罚风险、人员证书有效性、信用分适用地区和有效期 | 信用平台记录、主管部门公告、证书信息、招标资格要求 |

#### 标签字段扩展

政策与规则候选增加：

```json
{
  "ai_tender_tags": ["tender_doc_check"],
  "risk_level": "low|medium|high",
  "evidence_required": ["official_policy", "project_document", "platform_record"],
  "decision_mode": "hint_only|human_review_required|blocking_rule",
  "false_positive_notes": "围串标类只提示风险，不作定性结论"
}
```

#### 默认处理原则

- 招标文件检测、投标合规自查：可以形成可执行检查清单。
- 围串标特征：只输出“风险特征”和“需复核证据”，不得直接定性违法。
- 信用管理：必须带来源平台、查询时间、有效期；过期信用信息不得作为当前结论。
- 四类标签都必须保留 `source_refs`，未核验官方依据前仅进入 `candidate`。

### 5. 更新机制

- 每周增量检查官方来源；无变化不输出主聊天消息。
- 新增或变更政策先进入 `candidate`。
- 经核对官方原文后改为 `verified`；到执行日改为 `effective`。
- 出现替代文件时建立 `superseded_by` 关系，不覆盖旧记录。
- 仅在高价值变化、影响当前项目或需要人工确认时通知。

### 6. 验收标准

- 任一政策结论能回溯官方 URL、原文证据和审核人。
- 能按地区、主题、执行日期、专业检索。
- JARVIS 审核上下文只注入与当前项目地区/日期匹配的规则。
- 过期或被替代规则不会作为当前有效规则直接推荐。

## 四、实施顺序

### P0（立即可做）

- 使用本方案中的字段约定。
- 建立政策种子台账，先登记已有 3 条情报，状态设为 `candidate`，不把日报摘要当官方证据。
- 新任务开始记录 `cost_tier` 和 `promotion_reason`。

### P1（下一次开发迭代）

- 扩展 file-intake 请求/响应模型，增加 `city/project_date/pricing_standard/rule_resolution`。
- 增加 L0 地区与标准号抽取器。
- 增加任务成本日志和按日汇总。

### P2（样本验证后）

- 把已核验政策转换为 source pack，进入 staging 审核链。
- 在 OpenClaw review context 中注入地区规则证据。
- 用 10 个跨地区项目做回归，不通过则保持为提示信息，不参与自动决策。

## 五、本轮不做

- 不直接修改 OSS/LTR 候选召回、排序或阈值。
- 不把未经官方原文核验的日报内容写成正式规则。
- 不新增定时任务；政策跟踪频率和通知渠道由现有情报任务承接或另行确认。
