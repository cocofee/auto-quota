# 匹配架构收口方案

## 1. 当前代码里的实际主链

现有在线主链不是单文件，但从入口到收尾基本是：

1. `src/match_engine.py:662` `match_search_only(...)`
2. `src/match_pipeline.py:4119` `_prepare_item_for_matching(...)`
3. `src/query_builder.py:1793` `build_quota_query(...)`
4. `src/match_core.py:1041` `_prepare_candidates(...)`
5. `src/reranker.py` 基础 rerank
6. `src/param_validator.py` 参数校验 + rectify
7. `src/match_pipeline.py:3819` `_build_search_result_from_candidates(...)`
8. `src/ltr_ranker.py:409` `rerank_candidates_with_ltr(...)`
9. `src/candidate_arbiter.py:176` `arbitrate_candidates(...)`
10. `src/match_engine.py:755` `rule_validator.validate_results(results)`
11. `src/consistency_checker.py:184` `check_and_fix(results)`
12. `src/final_validator.py:152` `validate_results(results)`

结论：

- 现在不是一个“排序器”在决定 top1。
- 现在是“召回后有多层模块都可能改 top1”。


## 2. 现有模块到目标架构层的映射

### A. Parser / TopicExtractor

职责：只抽结构，不判定定额。

当前对应：

- `src/text_parser.py`
- `src/query_builder.py`
- `src/bill_cleaner.py`
- `src/context_builder.py`

现状问题：

- `query_builder` 已经不只是“构造查询”，还夹带了主体发现、同义扩展、部分路由意图。
- `text_parser` 和 `query_builder` 的边界不清。


### B. Router

职责：只决定搜哪些库、哪些册、哪些章节。

当前对应：

- `src/match_pipeline.py:_build_classification(...)`
- `src/query_router.py`
- `src/specialty_classifier.py`
- `src/unified_planner.py`
- `src/universal_kb.py`

现状问题：

- 路由信息分散在 `classification / query_route / unified_plan / plugin_hints`。
- 有的“显式家族选择”已经越过路由，直接在后面抢 top1。


### C. Retriever

职责：只把候选拉进池子，不决定最终答案。

当前对应：

- `src/match_core.py:974` `cascade_search(...)`
- `src/hybrid_searcher.py`
- `src/vector_engine.py`
- `src/quota_db.py`
- `src/experience_db.py`
- `src/match_core.py:617` `try_experience_match(...)`

现状问题：

- 搜索召回、经验直通、rule backup injected 都混在一起。
- “经验命中”有时是召回，有时是直通裁决，语义不统一。


### D. Ranker

职责：唯一允许决定 top1 的层。

当前实际参与者：

- `src/reranker.py`
- `src/param_validator.py`
- `src/ltr_ranker.py`
- `src/candidate_arbiter.py`
- `src/match_pipeline.py:_promote_explicit_distribution_box_candidate(...)`

现状问题：

- 这里已经形成“多排序器并存”。
- `param_validator` 不只是 validate，还会 `rectify`。
- `ltr_ranker` 会改排序。
- `candidate_arbiter` 会改排序归属。
- `match_pipeline` 里还有显式 candidate promote。


### E. Veto / FinalCheck

职责：只做硬否决，不推荐新答案。

当前对应：

- `src/final_validator.py`
- `src/review_checkers.py`
- `src/review_correctors.py`
- `src/rule_post_validator.py`
- `src/consistency_checker.py`

现状问题：

- `final_validator` 现在不是纯 veto，存在 fallback 替换 top1。
- `review_checkers + review_correctors` 是一套“查错 + 改错”机制。
- `consistency_checker` 也会改结果。


### F. LLM Review

职责：只处理低置信度、长尾、人工复核辅助。

当前对应：

- `src/match_engine.py:790` `match_agent(...)`
- `src/agent_matcher.py`
- `src/llm_verifier.py`
- `src/unified_knowledge.py`

现状问题：

- LLM 链路和 search 链路是并存的，但在线主链收口还不够严格。
- 离线学习资产与在线主链的接口还不够清楚。


## 3. 当前真正的越权点

按“谁在改 top1”看，当前高风险点如下。

### 一级风险：直接重排或替换

1. `src/param_validator.py`

- `validate_candidates(...)` 之后会调用：
  - `_tier_rectify`
  - `_logic_rectify`
  - `_context_rectify`
  - `_feature_rectify`
  - `_family_gate_rectify`
- 这不是纯校验，是校验 + 排序纠偏。

2. `src/ltr_ranker.py`

- `rerank_candidates_with_ltr(...)` 会基于 LTR 和 CGR 重排。

3. `src/candidate_arbiter.py`

- `arbitrate_candidates(...)` 会用主参数、结构分、搜索分挑 challenger，改变 top1。

4. `src/final_validator.py`

- `_find_next_candidate_fallback(...)`
- `_apply_veto_fallback(...)`
- 这已经是“最终阶段替换答案”。

5. `src/consistency_checker.py`

- `check_and_fix(results)` 从名字和调用位置看，也是后置改答案。


### 二级风险：规则式局部 promote / override

1. `src/match_pipeline.py`

- `_pick_explicit_*_candidate`
- `_promote_explicit_distribution_box_candidate`
- `_inject_rule_backup_candidate`
- `_apply_rule_backup`
- `_apply_similar_exp_backup`

这些逻辑虽然分散，但本质上都在影响最终 top1。


## 4. 目标架构

目标只保留一条主链：

`InputNormalizer -> TopicExtractor -> Router -> Retriever -> UnifiedRanker -> HardVeto -> Output`

约束如下：

### 4.1 TopicExtractor

输出：

- `primary_subject`
- `structured_fields`
- `key_specs`
- `noise_spans`

禁止：

- 不允许返回 quota
- 不允许决定章节
- 不允许决定 top1


### 4.2 Router

输出：

- `search_books`
- `search_sections`
- `route_profile`

禁止：

- 不允许挑 candidate
- 不允许改分
- 不允许 override top1


### 4.3 Retriever

输出：

- `candidate_pool`
- `candidate_source`

禁止：

- 不允许最终排序
- 不允许删掉有价值候选


### 4.4 UnifiedRanker

唯一允许决定 top1。

输入特征来源：

- 基础文本分：`reranker.py`
- 参数匹配分：从 `param_validator.py` 抽出 feature，不再 rectify
- LTR 分：`ltr_ranker.py`
- 结构化来源信号：`candidate_arbiter.py` 抽成 feature
- 显式家族信号：`match_pipeline.py:_pick_explicit_*` 抽成 feature

目标：

- `ranker` 统一产出 `topk`
- 其他层不再重排


### 4.5 HardVeto

只留硬否决：

- 单位冲突
- 册别/专业大类硬冲突
- 明确不可能的锚点冲突

禁止：

- 不允许自己找 fallback candidate
- 不允许自己推荐替换项
- 不允许纠正到另一个 quota


## 5. 不重写系统的收口方案

### P0. 先固定接口，不动算法

先在概念上固定六层接口：

- `topic`
- `route`
- `retrieve`
- `rank`
- `veto`
- `final`

先让 trace 全部按这六层出。


### P1. 把“会改 top1”的模块登记出来

必须登记的当前 top1 changer：

- `param_validator`
- `ltr_ranker`
- `candidate_arbiter`
- `match_pipeline` explicit promote / backup inject
- `consistency_checker`
- `final_validator`

后续每收一个，就从“改 top1”改成：

- 产出 feature
- 或产出 veto flag


### P2. 先收 `param_validator`

这是最优先的，因为它最像“伪排序器”。

目标：

- 保留 `validate`
- 去掉 `rectify`
- 把 rectify 产出的信息改成 feature


### P3. 再收 `candidate_arbiter`

目标：

- 不再直接挑 challenger 覆盖 top1
- 改成 `source / main_param / anchor_family` 特征


### P4. 再收 `final_validator`

目标：

- 去掉 `_apply_veto_fallback`
- 只返回 `vetoed / issue_type`


### P5. 最后收 `match_pipeline` 里的显式 pick/promote

目标：

- `_pick_explicit_*` 从 override 变成 rank signal
- `_promote_explicit_distribution_box_candidate` 从 promote 变成 bias feature

## 7. 2026-03-29 执行状态

主架构收口到这里，P2-P5 已基本完成，主链已经从“多处抢 top1”收成了：

`parser/query -> retriever -> ranker -> veto -> output`

已完成：

- `P2 param_validator`
  - 主链上不再做 rectify 改 top1，改成输出校验特征和 advisory。
  - 相关文件：`src/param_validator.py`、`src/match_core.py`

  - 相关文件：`src/candidate_arbiter.py`、`src/match_pipeline.py`

  - 相关文件：`src/final_validator.py`
- `P5 match_pipeline explicit pick/promote`
  - 显式 pick/promote 在主链上改成 annotation/advisory，不再直接成为排序权威。
  - 相关文件：`src/match_pipeline.py`
- 主链尾部清理
  - `match_engine` 主路径已去掉 `rule_validator.validate_results(results)` 的最终改答案动作。
  - 相关文件：`src/match_engine.py`

说明：

- `consistency_checker` 当前仍在调用链里，但已不是这轮低分的主因。
- 当前低分已经不再主要是“后处理改坏”，而是主链真实问题暴露出来。


## 8. 收口后评测结论

全省 closed-book smoke 结果：

- 数据集：`805`
- 正确：`273`
- 命中率：`33.9%`
- `oracle_in_candidates`：`526`
- `oracle_not_in_candidates`：`279`

错误阶段分布：

- `retriever`: `279`
- `ranker`: `235`
- `ltr_ranker`: `18`

主因分布：

- `wrong_book`: `192`
- `synonym_gap`: `187`
- `wrong_tier`: `130`
- `no_result`: `23`

结论：

- 主架构问题已经基本收住。
- 当前瓶颈不再是“谁来决定 top1”，而是：
  - 进错册/错家族
  - 术语不对称导致召回不到
  - 同家族内档位排错


## 9. 当前最合理的下一步

不再继续做架构重构，只按评测三桶推进，顺序固定：

1. 先做 `wrong_book`
2. 再做 `synonym_gap`
3. 最后做 `wrong_tier`

执行约束：

- 一次只打一桶，不并行开三条线。
- 每做一步先看评测，再决定下一步。
- 不再新增会改 top1 的后处理模块。


## 10. 当前立即执行项

只做一件事：

### 先做 `wrong_book` 样本归因表

按错例列清楚：

- 具体省份/册别
- 当前 query / route / candidate pool
- oracle 实际所在册
- 是路由偏了，还是检索范围放大后被错册抢走
- 是否存在索引缺失或库资产异常

原因：

- 这是当前第一大错因。
- 现在再动排序器，收益不如先把错册压下去。
- `wrong_book` 压不住，后面的 `synonym_gap/wrong_tier` 都会被噪声放大。

这一步已经基本完成。下一阶段不是继续收架构，而是按：

- `wrong_book`
- `synonym_gap`
- `wrong_tier`

逐桶清理主链真实误差。
